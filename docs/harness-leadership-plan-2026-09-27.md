# CoWork OS harness leadership: evidence and execution plan

Prepared 27 September 2026. Planning deliverable; implementation and competitive performance are not claimed.

**Decision:** make verified completion, reliable recovery, and cost per accepted result the engineering objectives. Keep coding performance a first-class requirement. Build on CoWork's existing runtime and work-session contracts, repair demonstrated correctness gaps, and make each optimization earn promotion through independent outcome tests.

The ambition is to outperform Codex, Claude Code, Cursor, and Hermes on a declared, demanding portfolio. A credible path starts with reproducible wins in specific task families and expands; a universal superiority claim cannot be established by source inspection, feature breadth, or a passing unit suite.

## What changes from the supplied report

The report's direction is sound, but it undercounts existing infrastructure. `WorkSessionContractRepository` already stores outcome contracts, constraints, evidence manifests, artifact revisions, waits, and child outcomes. `WorkSessionProtocolRepository` already has canonical items and idempotency keys; `WorkSessionActivityLeaseRepository` already stores liveness leases. Extend these authorities after checking their callers. A new parallel framework, contract database, or event journal would increase migration and consistency risk.

One concrete gap is visible in `WorkSessionContractService.recordTaskTerminal()`: when the task outcome is complete, it marks every contract requirement satisfied. This is a terminal-state projection, not independent proof of each requirement. Preserve the useful storage model, but make completion consume requirement evidence rather than use completion to manufacture satisfaction.

The evaluation gap is also more specific than “needs more tests.” The current repository has meaningful deterministic gates. However, incident JSON specifications are not automatically executable outcomes, and the live battery checks PDF/PPTX outputs only for a nonempty file. Its polling loop also auto-approves pending requests. Those are suitable starting points for a disposable smoke harness, not proof of safe autonomous artifact quality.

The file-edit race is now reproduced against the actual `EditTools` class: two writers read the same inode, pause at mutation-baseline capture, and both report success after one overwrites the other's independent edit. The report's standalone DAG findings have a different applicability: production uses `OrchestrationGraphEngine`, with per-node storage and restart reconciliation, while no production caller of `SubAgentOrchestrator` was found. Do not replace the production graph to repair an unused class.

Cancellation already cascades through native children, and per-executor cost/token guardrails already exist. The actionable budget gap is joint admission: inspected live spawn/graph paths do not carry a shared reservation across the task tree. Likewise, event dedupe and liveness leases do not establish exactly-once tool effects. Two live-graph boundaries need immediate fault tests: child/remote dispatch occurs before its task identifier is persisted on the node, and parent cancellation's native-child traversal does not itself traverse remote ACP graph nodes. These are source-supported failure hypotheses, pending runtime reproduction.

Authority also needs a narrower correction than “add approval binding”: approval fingerprints and revalidation already exist. However, the researcher role's read-only label/`mutationAllowed: false` does not trigger the stronger boundary used for verifier/helpers; researcher children can inherit a full-authority parent's mode and shell access. This is a confirmed configuration-contract gap, with browser/connector mutation routes still unexecuted hypotheses. Test that role boundary before expanding delegation. Separately, test credential redaction and export policy across raw-transcript compaction fallback and configured provider failover; no disclosure was observed in this audit.

Detailed source findings and validation evidence are in [the audit register](/Users/mesut/Downloads/app/cowork/docs/harness-audit-evidence-2026-09-27.md).

## What “better” must mean

Use three separate comparisons, with product/runtime/version recorded for every result:

| Track | Fair comparison | Permitted conclusion |
| --- | --- | --- |
| Controlled native harness | Same accessible model/version, reasoning settings, environment, task inputs, tools and budgets where supported; document remaining differences | Evidence about native harness changes within the matched subset |
| Best supported product | Native CoWork versus each product's sensible supported configuration, including its own models and supervision | Evidence about the user's actual product choice |
| Delegated engine | CoWork invoking Codex/Claude or another external engine, identified explicitly | Evidence about CoWork's orchestration/integration value; not a native-loop win |

The primary metric is independently verified task success per attempt. Report false completion, user intervention minutes, all-in cost per verified success, elapsed p50/p95, repeat-trial reliability, recovery outcomes, unauthorized effects, and unsupported tasks alongside it. Cost per verified success is total spend on all attempts divided by verified successes; with no successes it is undefined, not zero. Failed attempts, retries, routers, verifiers, children, and paid tools belong in cost. Missing usage remains visible and conservatively bounded; it is not zero. For subscriptions, report observed usage and the allocation method separately from an API-price proxy; with materially incomplete cost data, do not claim cost superiority.

**Proposed promotion targets, to calibrate after a pilot:** no new critical integrity or authority failure in the mandatory adversarial suite; core coding success non-inferior within a predeclared 3-percentage-point margin; and either a supported quality improvement or at least 25% lower all-in cost at non-inferior quality. A first leadership target is a 10-point verified-success gain on hard recovery/cross-domain workflows without a material coding regression. These are decision thresholds, not predicted results.

An unqualified “better than all four” claim requires convincing results against all four across the named portfolio, including coding. Passing a recovery milestone alone does not earn that claim. Use paired comparisons and uncertainty clustered by task, not by repeated attempt; preregister weighting, margins, exclusions, and primary comparisons. An inconclusive interval means inconclusive, not parity. Publish losses and safety failures as well as wins.

For a confirmatory release, check integrity failures first, coding non-inferiority second, then the preregistered primary quality **or** cost endpoint. Use simultaneous familywise 95% confidence bounds across the four named comparisons; choose the exact task-clustered procedure before opening the holdout. Other family/ablation findings are exploratory until separately confirmed. Zero observed safety failures is a release condition, not proof of zero risk.

## Competitive lessons and the potential advantage

| Comparator | Mechanism verified in primary documentation | CoWork response |
| --- | --- | --- |
| Codex | Model-specific instructions, stable prompt prefixes, and explicit compaction underpin its loop. [OpenAI engineering](https://openai.com/index/unrolling-the-codex-agent-loop/) | Qualify model profiles over one kernel; measure full request and cache behavior before changing discovery/routing. |
| Claude Code | Subagents have separate context and configurable tool/permission boundaries. Checkpoint rewind has documented limits for shell and many subagent edits. [Subagents](https://code.claude.com/docs/en/sub-agents), [checkpointing](https://code.claude.com/docs/en/checkpointing) | Match useful isolation; test recoverability across owned processes, children, files and remote effects. Do not confuse a checkpoint with rollback of external effects. |
| Cursor | Long tool output and history can be retrieved from files; MCP detail is discovered on demand. Its scaling account reports that an extra integrator role became a bottleneck. [Context discovery](https://cursor.com/blog/dynamic-context-discovery), [scaling experiments](https://cursor.com/blog/scaling-agents) | Preserve exact tool results and retrieve selectively. Use deterministic merge admission plus an accountable owner; add an LLM coordinator only when an ablation justifies it. |
| Hermes | Delegation documentation covers ownership-based cancellation, explicit unknown status after a running child is interrupted by restart, and optional worktree isolation with stated limitations. [Delegation](https://hermes-agent.nousresearch.com/docs/user-guide/features/delegation) | Build on explicit uncertainty; aim to demonstrate safe reconciliation and resumed work. Enforce and expose isolation guarantees instead of silently assuming them. |

These are mechanisms and documented boundaries, not measured product rankings. “Has multiple providers,” “has agents,” “has memory,” and “does office work” are insufficient differentiators.

**The advantage to prove:** a user can create, inspect, correct, interrupt, resume, and repeat a real workflow across code, files, browser, and connectors while retaining verified artifacts, authority, and cost control. Changing a provider must preserve the task/effect state and its privacy constraints. This is a hypothesis to test, not a capability claim.

## Architecture decisions

Retain `SessionRuntime`/`TurnKernel`, `ToolScheduler`, `ToolPolicyPipeline`/`PermissionEngine`, `VerificationRuntime`, the work-session repositories, transcript/checkpoint stores, and existing provider adapters. Extract responsibilities from large executor/daemon files incrementally, under behavior-preserving tests.

1. **One canonical task state.** Extend the existing outcome contract with revisioned user requirements and structured proof status. Keep legacy completion/projection fields compatible; mark historical claims as legacy/unverified when no proof exists. User corrections invalidate affected requirements without erasing prior artifacts.
2. **Separate execution status from verified outcome.** A tool's success, a child's completed state, and a fluent final answer are evidence inputs. Mandatory requirements need fresh checks or an explicit unverified/blocked result. Keep the reviewer read-only; obtain fresh executable proof through a narrowly authorized verification runner in an isolated artifact copy, with its own receipt and budget. Do not grant a reviewer broad write/network power just to run tests. Only the user can authorize weakening a requirement or an applicable waiver.
3. **Durable intent and external receipts.** Add missing per-effect records within the existing persistence authority, after inventorying current dedupe. Record intent before dispatch and result/remote ID afterward. Reconcile an ambiguous send/update before retry; use provider idempotency where available. Replay rebuilds state without performing actions.
4. **Authority at dispatch.** Bind the approved arguments, resource scope, role, environment, and policy version. Revalidate after an approval wait or revocation. Child permissions cannot exceed the intersection of parent grant, workspace policy, role and executor capability. External engines disclose boundaries they cannot enforce.
5. **One reserved budget and cancellation owner per task tree.** Reserve before model/child/helper dispatch, settle usage, keep a verification allowance, and stop new admission when exhausted or cancelled. Track in-flight remote uncertainty separately from local stop acknowledgement.
6. **Exact evidence outside the prompt.** Store the original authorized/redacted payload with hash, timestamp, scope, retention metadata, and range/search retrieval. A prompt summary is a view. Refetching a changed source cannot replace evidence from the original observation.
7. **A qualified model profile, not an uncontrolled alternate loop.** Record protocol, tool schemas, reasoning settings, context estimator, cache policy, supported modalities, retry behavior and known limitations. Provider fallback retains authorization, privacy and unresolved-effect state.

Persist versioned contracts and feature flags per run. Shadow only pure decisions/projections, never execute a mutating action twice. Prefer adding narrowly required columns/tables and adapters over parallel authorities. Migrations must read old runs and define rollback before enforcement becomes default.

The first ten working days are a planning window for a maintainer using coding agents, not a deadline commitment. Limit concurrent write ownership to independent surfaces; independent review and final integration remain accountable work.

## Benchmark specification

Start with **one or two validated smoke tasks per configuration**, with explicit maximum spend, attempts and elapsed time configured before any paid call. The runner refuses an absent cap and stops new admission at the cap; reconcile outstanding spend before continuing. Use the observed per-attempt costs to size and cap the next stage.

Then use **24 development tasks**: eight coding, four long-horizon recovery, and three each for research, office artifacts, browser work and connector work. Two attempts per supported configuration reveal runner/grader defects and cost variance. Five configurations (native CoWork plus the four requested competitors) would mean up to **240 attempts**, before adding model-controlled or delegated-engine configurations. This pilot is not powered to prove superiority. It is for runner/grader repair, development ablations and sizing, not final claims.

The [concrete pilot catalog](/Users/mesut/Downloads/app/cowork/docs/harness-development-pilot-2026-09-27.md) specifies all 24 setups, independent oracles, supported surfaces and known-negative submissions. Fixtures are designed, not yet implemented or executed. Internal CoWork crash/failpoint cases are supplemental and never scored as competitor failures.

Then freeze a separately held **200-task portfolio**: provisionally 80 repository coding tasks and 24 each for research, artifacts, browser, connectors and long-horizon recovery. Tag tasks across those families for memory, delegation and permission stress so those behaviors are not confined to a toy stratum. Use pilot variance and the desired coding claim to adjust allocation/sample size before preregistration. Five trials × 200 tasks × five configurations is **5,000 attempts**, not 4,000; extra tracks add attempts. Obtain the actual spend cap from observed pilot cost before scaling.

Eighty coding tasks repeated five times are still 80 task clusters. Before opening the holdout, simulate power using paired task disagreement and within-task variance for the 3-point coding margin and primary comparisons. Lock the sample size, margins, confidence procedure and stopping rule. If an affordable sample cannot resolve the margin, report inconclusive and narrow the claim; do not reinterpret a nonsignificant difference as parity or tune the threshold after seeing holdout outcomes.

Report two views: a paired **jointly supported task/surface subset**, and **full-portfolio coverage/completion**, where unsupported or missing-configuration entries remain visible as not completed. Preserve separate terminal causes for product/setup failure, infrastructure error, timeout, safe stop and candidate failure; freeze retry/exclusion rules and retain all rows. A safe stop passes only when the task's oracle expects it. Keep Harbor/headless and native desktop/browser results separate until their interaction surfaces are comparable.

Set aggregate weights independently from task allocation: a provisional product-choice view gives coding 50% and the five other families 10% each, reflecting the stated coding ambition while testing breadth. Freeze or revise these weights before the holdout, and always show family results and support coverage alongside the aggregate. A weighted average alone cannot establish dominance. Randomize configuration order, reset equivalent state for cold trials, and report warm-cache/memory conditions separately.

Use Harbor's existing comparator integrations and a native CoWork installed-agent adapter. Pin the framework, task revision, product package/binary, model settings and environment; do not rely on moving `latest` tags. A supported MCP integration does not prove a configured service works. [Harbor agents](https://docs.harborframework.com/core-concepts/agents/pre-integrated-agents), [custom agents](https://docs.harborframework.com/core-concepts/agents/custom-agents)

Put graders outside the candidate's writable environment; validate them against known correct, incorrect, corrupted and exploit-seeking submissions. Harbor has a separate verifier environment option; configure it explicitly instead of assuming the default isolates grading. Browser/native desktop outcomes need their own real UI and backend/read-back fixtures. [Harbor separate verifier](https://docs.harborframework.com/core-concepts/tasks/separate-verifier)

Each run manifest records task/requirements, source and executable hashes, starting dirty state, environment, model/provider parameters, tool/permission/skill/memory versions, budgets/concurrency, cache state, all usage including missingness, process/effect/artifact evidence, grader version, interventions and terminal reason. Grade final environmental state rather than trusting the final message. [Anthropic evaluation guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

Mandatory fault cases include same-inode edits, symlink/inode replacement, failed partial writes, kill before/after dispatch and receipt, permission revocation during approval, truncated streams, duplicate IDs/events, missing usage, compaction losing an early correction, unavailable credentials, cancelled children, merge conflicts, stale memory, poisoned retrieved instructions, and uncertain remote mutation. A blocker deliberately requested by the user can be a correct controlled stop; do not reward fake completion to improve success rate.

Keep development tasks, held-out evaluation, and consented real-user workflows separate. Prevent trial-to-trial memory leakage unless testing learning explicitly; publish cold/warm conditions separately. Report unsupported capabilities as support gaps, infrastructure failures with their predetermined handling, and all terminal statuses without selective removal.

## Rollout and stopping rules

Promote in gates: **trustworthy local baseline → safe native execution → measured task gains → useful scale → replicated competitive claim**. Each gate includes desktop/CLI/daemon builds where affected, appropriate regression suites, schema upgrade tests, and fresh execution of the changed route. Passing unit tests never substitutes for live workflow acceptance.

Feature-flag semantic changes independently. Abort promotion on user-file loss, unauthorized effects, invalid proof acceptance, hidden budget leakage, or a material coding regression. Keep prior execution contracts readable; preserve unknown effects for reconciliation during rollback. A routing/context/memory optimization with no measured gain stays disabled or is removed.

Test the first complete user journey with a small consented pilot: produce a checked artifact, make an exact revision, change/contradict its inputs, interrupt and resume, then repeat on another day. Measure accepted output and correction time, not completion counts or downloads. The prior continuity-and-control positioning remains a hypothesis; new runs must substantiate it.

The immediate starting work is P01–P04 plus the first P06 and P08a regressions. That yields a safer editor, a truthful completion contract, an enforced research role, and a measurement loop capable of deciding what engineering work actually makes CoWork better.
