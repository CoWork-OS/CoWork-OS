# Modular Mermaid parser build

`mermaid-parser-plugin.mjs` adapts the source of `@mermaid-js/parser` 2.0.1 for the production renderer build. The published package prebundles all 15 generated grammars, Langium and language-server utilities into one shared module. Rebundling the original modular source restores useful language loading boundaries. No grammar, service factory, validator, token builder, AST helper or runtime export is removed.

The installed package ships 47 original TypeScript sources in its source maps. The 18 forwarding/type-only barrels erased during upstream bundling are retained in `upstream-barrels.json`, from the official [Mermaid 12.1.0 source](https://github.com/mermaid-js/mermaid/tree/mermaid%4012.1.0/packages/parser/src). The original parser license is retained in `LICENSE` and emitted as `assets/mermaid-parser-LICENSE.txt` with the application. The plugin performs no network requests or dependency installation.

The build fails on an unsupported Mermaid/parser/Langium version, changed/missing/additional source content, unexpected generated declarations, altered cache ownership, unknown mapped imports, or a different parser package instance. It resolves the parser from Mermaid's own package location, including nested installations. `source-lock.json` records SHA-256 hashes for all 65 original sources. Direct Langium 4.4.0 is the upstream parser's declared runtime-development version; its ordinary ESM browser modules replace the embedded runtime.

Generated grammar and service-module declarations are partitioned with TypeScript's AST. Each declaration's text stays verbatim, including its private mutable grammar cache. Generated import bindings point directly to their owning module; the existing parse entry and all 15 dynamic initializers remain unchanged. Only the 18 forwarding/type-only barrels have `moduleSideEffects:false`, after AST validation that they contain no runtime bodies. Implementation modules retain normal bundler side-effect analysis. A separate shape check rejects top-level registrations, calls and mutations; the only explicit eager constructors are the original generated reflection singleton and private validator string Sets. Generated terminal namespaces only contain regex constants and type declarations.

Three upstream re-exports are type-only without being marked as such. Their type-only status is derived from the original declarations before isolated TypeScript transpilation, matching upstream whole-program type erasure. No runtime name is changed.

Run `npm exec -- vitest run tests/mermaid-parser-modular.test.ts --maxWorkers=1` to compare the real Vite-built adapter with the untouched published parser. The checks cover the complete runtime export set, nonempty valid and two rejected inputs for every language, AST data/parents, CST token spans, reference text/errors, public parse failures, service metadata, grammar-cache identity across service factories, resolved references and validation diagnostics, source/version/shape drift, and actual emitted JavaScript sizes. Node's parity build disables only browser module-preload link insertion; production preload behavior is exercised by the renderer acceptance run. `parity-cases.json` supplies the same 15 verified examples for browser acceptance.

When updating Mermaid, refresh this adaptation deliberately against the new published package and official barrels, inspect source and dependency changes, then rerun all parity and production renderer checks. Do not update hashes alone to bypass a source-shape or behavior failure.
